# Capability — shared bits across the three §5 capability-handshake adapters

**Pipeline role:** Not a pipeline stage of its own — a shared support module for `GrpcCapabilityAdapter/`, `HttpCapabilityAdapter/`, and `ZmqCapabilityAdapter/` (Stage 13/11/12, part of the message-versioning capability-handshake effort shipped 2026-08-23). Factors out the two things genuinely identical across all three transport-specific slices: which message types get advertised, and the transport-agnostic client-side dispatch logic.
**Entry points:** `Capability.capability_common.message_type_names(messages)` (Python, generation time) and `harpia::capability::Dispatcher` (C++, copied into every generated project's `generated/cpp/capability/`).
**Inputs → Outputs:** `capability_common.py` has no adapter of its own — it's imported by the three real adapters. `runtime/harpia_capability_dispatch.h` is copied verbatim (like `XmlAdapter/runtime/harpia_xml.h`) by all three of them into the same shared `<dest>/generated/cpp/capability/` directory.

## Files
- `capability_common.py` — `DISPATCH_RUNTIME`/`DISPATCH_RUNTIME_SRC` (the path to the shared dispatch header, so each adapter's `copy_if_different` call doesn't hardcode a path into a sibling module) and `message_type_names(messages)` (`sorted({m.name for m in messages if not m.isEnum})` — every non-enum message type, regardless of `tableName`: capability is about whether the peer's generated code knows the type exists at all, not whether it has DB backing). Deliberately tiny — each adapter still owns its own template/runtime; this only exists so the three don't drift on these two specific things.
- `runtime/harpia_capability_dispatch.h` — hand-written (NOT generated), transport-agnostic. `Dispatcher`: `on(type, handler)` registers a per-type handler; the constructor takes a **mandatory** fallback (no default), so "nothing wired up for an uncovered type" is structurally impossible to express, not just a documented convention. `dispatch(type, peer_capabilities)` calls the handler only when both the peer's set covers `type` *and* a handler was actually registered for it; otherwise the fallback runs. Same "harpia wires the capability, caller supplies the logic" split as `Database/MigrationAdapter`'s `data_transform` hook — this class is dispatch scaffolding only; the schema author supplies what "send it" / "fallback" actually do. Used the same way regardless of which transport's `negotiate()` produced the peer's `std::set<std::string>` capability set.

## Key facts / gotchas
- **Extracted from `GrpcCapabilityAdapter/runtime/harpia_capability.h`** partway through building the REST/SOAP/ZMQ slices, once it became clear `Dispatcher` has zero gRPC-specific code in it (`std::function`/`std::map`/`std::set`/`std::string` only) — duplicating it three times (once per transport runtime) would have been the wrong call the moment a second transport needed it. Tested once, in `tests/test_message_versioning_capability.py` (the gRPC test file) — not re-tested per transport, since it's the same class regardless of which `negotiate()` populated the `std::set<std::string>` passed to `dispatch()`.
- **All three adapters copy this file into the SAME output directory** (`<dest>/generated/cpp/capability/`), not three separate per-transport directories — that's a deliberate choice (see each adapter's own `Process()`): capability-handshake output for a project lives in one place regardless of which transport(s) that project uses, mirroring how `capabilities_service.proto`'s wire messages are shared across all three rather than each transport getting its own copy of the contract.
- Not itself called from `main.py` — it's a dependency of the three adapters that are.

## Touchpoints
- Depends on: nothing beyond the C++ standard library (the runtime header) and `os` (the Python helper).
- Depended on by: `GrpcCapabilityAdapter/GrpcCapabilityAdapter.py`, `HttpCapabilityAdapter/HttpCapabilityAdapter.py`, `ZmqCapabilityAdapter/ZmqCapabilityAdapter.py`.
