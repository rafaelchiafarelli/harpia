# JavaRestAdapter — Java target: REST CRUD over JDK-builtin HttpServer

**Pipeline role:** Java-target Stage 12 equivalent (sessions J.12 routing/credential-gate scaffolding, J.13 CRUDL handlers, J.14 acceptance gate — landed together, `Initiatives/multi-language-targets/thread-1-java-target`). Routes on `com.sun.net.httpserver.HttpServer` (JDK-builtin, zero dependency — the recommendation `../../README.md` §2 makes, same "least new dependency surface" reasoning as the XML runtime picking `javax.xml`), backed by `JavaDatabase`'s CRUDL DAOs, content-negotiated via `JavaJsonAdapter`/`JavaXmlAdapter`.
**Entry point (from main.py):** gated behind `HARPIA_GEN_LANG=java`, called right after `JavaXmlAdapter` in the same block: `JavaRestAdapter(messages=msgFactory.messages, dest=testDestination, compliance=complianceContext).Process()`. Returns `None` or an `Error` (non-fatal; main.py logs it).
**Inputs → Outputs:** consumes message objects (same table-bearing filter as `Database/RestAdapter.py`: skip enums and messages with no `tableName`). Emits `<dest>/java/src/main/java/com/harpia/runtime/rest/HttpRestHelpers.java` (shared) and `<dest>/java/src/main/java/com/harpia/generated/rest/<name>_rest.java` (one per table-bearing message).

## Files
- `runtime/HttpRestHelpers.java` — hand-written (NOT generated), copied verbatim. Message-agnostic HTTP mechanics shared by every generated `<name>_rest.java`: `authorized(exchange, user, pswd)` (the Stage 5 `X-User`/`X-Pswd` credential gate — parameterized instead of per-message string-literal closures the way C++'s `authorized_<name>()` needs, since Java doesn't need a separate function per message just to close over two literals), `wantsXml`/`isXmlBody` (content negotiation), `parseBody`/`sendMessage`/`sendBody`/`sendStatus` (all generic over `Message`/`Message.Builder`, reusing the already-generic `HarpiaJson`/`HarpiaXml`), and `trailingId(exchange, collectionPath)` — the routing-gap-filler `HttpServer` needs: it only matches a request to the *longest registered context path that prefixes it*, with no built-in `:id`-style path variable support the way Crow's `route_dynamic("<base>/<name>/<int>")` gives the C++ target, so one context registered at the collection path handles both the collection AND every item request, and this helper recovers which one it was.
- `templates/rest.java.tmpl` — per-message `com.harpia.generated.rest.<name>_rest`: `register(HttpServer, Connection, String base)` wires one `HttpServer.createContext` at `<base>/<name>`; `handle()` dispatches by HTTP method + whether `trailingId` found an id; `list`/`read`/`create`/`update`/`remove` call straight into `<name>_dao` and `HttpRestHelpers`. Per-message generation (unlike JSON/XML's single shared class) because each handler needs the concrete `<name>`/`<name>.Builder`/`<name>_dao` types — there's no common `Dao<T>` interface in this repo to dispatch through generically, and DAO generation is already this codebase's established pattern for this kind of per-type glue (`JavaDatabase`).

## Deliberately reduced scope (a direct consequence of JavaDatabase's own reduction)
`list()` is **unpaginated** — `?limit=`/`?offset=` query parameters are not read at all. This isn't an independent gap: `JavaCrudlAdapter` (J.6) never built the C++ target's paginated `list(out, offset, limit)` DAO overload (out of that session's own reduced scope, `JavaDatabase/CLAUDE.md`), so there is nothing for a pagination query parameter to call here. Lifting this needs the paginated DAO overload first, then this adapter's `list()`.

## Key facts / gotchas
- **HttpServer's context-matching, not a router library, decides collection vs. item.** Registering `<base>/<name>` as the ONE context means a request for `<base>/<name>/<id>` is delivered to the SAME handler (HttpServer's longest-prefix-match rule) — `HttpRestHelpers.trailingId()` is what tells `handle()` which case it's in. There is no equivalent of Crow's separate `col`/`item` route registrations.
- **The credential check, content negotiation, and error responses are pure HTTP mechanics with zero message-type knowledge**, which is exactly why they collapsed into one shared class instead of being generated per message the way the CRUDL glue is — the same "is this genuinely per-type, or just per-type-shaped boilerplate" question `JavaJsonAdapter`/`JavaXmlAdapter`'s CLAUDE.md docs already asked and answered the same way.
- `handle()` catches `IOException`/`SQLException` around the whole dispatch and responds 500 rather than letting an exception propagate out of an `HttpHandler` (which `HttpServer` would otherwise just log and hang the connection on) — this is the REST-specific analogue of `JavaDatabase/CLAUDE.md`'s "let `SQLException` propagate" choice for the DAO layer itself: the DAO throws, but a *handler* is a request/response boundary, so it must catch and turn a real failure into a real HTTP status instead.
- `register()`'s `Connection conn` must stay open for the registered routes' lifetime — same "caller keeps the session alive" contract `Database/RestAdapter.py`'s `register_<name>()` documents for its `soci::session&`.
