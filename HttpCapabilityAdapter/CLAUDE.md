# HttpCapabilityAdapter — REST/SOAP capability handshake (HTTP slice)

**Pipeline role:** Stage 11/12 (SOAP/REST). Ships a hand-written client runtime and emits ONE whole-project `GET <base>/capabilities` route advertising every message type the generated peer knows about — shared by REST and SOAP rather than each getting its own mechanism, since both register routes on the same `crow::SimpleApp` in a real deployment (see `Database/RestAdapter.py`/`Database/SoapAdapter.py`, both taking a `crow::SimpleApp&`). Part of the message-versioning capability-handshake effort (shipped 2026-08-23) — see `GrpcCapabilityAdapter/CLAUDE.md`/`Capability/CLAUDE.md` for the shared design and the sibling gRPC/ZMQ slices.
**Entry points (from main.py):** `HttpCapabilityAdapter(messages=msgFactory.messages, dest=testDestination, rootHash=rootFile.getHash()).Process()`. Returns `None` (no failure path today — pure text emission, nothing to fail on).
**Inputs → Outputs:** consumes the full `messages` list (via `Capability.capability_common.message_type_names`). Emits `<dest>/generated/cpp/capability/capabilities_<rootHash>_http.h` (route registration) and copies `harpia_http_capability.h` (client runtime) + the shared `harpia_capability_dispatch.h` into the same directory.

## Files
- `HttpCapabilityAdapter.py` — same shape as `GrpcCapabilityAdapter.py`: copies both runtime headers, renders the template with the baked-in type list.
- `templates/capabilities_http.h.tmpl` — `harpia::http_capability::register_capabilities(app, base)` registers `GET <base>/capabilities` on a `crow::SimpleApp`. The handler builds a `capabilities_Response` (the SAME wire message the gRPC slice defined) and serializes it via `google::protobuf::util::MessageToJsonString` — reusing protobuf's own JSON support rather than hand-building a JSON string, so the response is symmetric with `harpia_http_capability.h`'s `JsonStringToMessage` parse on the other end (protobuf's default camelCase field-name mapping, e.g. `message_types` -> `"messageTypes"`, is handled identically by both sides automatically). Needs the same `#ifdef _WIN32 / #include <windows.h> / #undef DELETE` guard before `#include "crow.h"` as `rest.h.tmpl`/`soap.h.tmpl` (see those files' comments for why). Deliberately ungated (no `X-User`/`X-Pswd` check) — same reasoning as gRPC's `GetCapabilities`.
- `runtime/harpia_http_capability.h` — hand-written (NOT generated). `negotiate(host, port, base, timeout_ms, on_legacy_peer = noop)` does a blocking HTTP/1.1 GET with a real connect+read timeout via a small raw-socket helper (`detail::http_get`), then parses the response body as a `capabilities_Response` via `JsonStringToMessage`. Any failure (connection refused, timeout, non-200 status, unparseable body) resolves uniformly to the plan's "legacy peer, no capability set" outcome. `detail::http_get` is a trimmed, GET-only sibling of `tests/harpia_test_client.h` (same reason that file exists: **Crow ships no HTTP client**) — not a general-purpose client, just enough to ask a peer "what do you support."

## Key facts / gotchas
- **REST and SOAP share ONE mechanism, not two.** No SOAP-envelope-specific capability operation exists or is planned — a plain HTTP GET is simpler and every SOAP deployment already runs on a Crow app alongside its REST routes (or could), so inventing a redundant envelope-wrapped equivalent would be pure duplication for no new coverage.
- **Whole-project artifact, not per-message** — same reasoning as `GrpcCapabilityAdapter`. Exactly one `capabilities_<rootHash>_http.h` regardless of schema size.
- **Only needs Stage 7 (`ProtoCompiler`), not Stage 13's `GrpcCompiler`** — the handler only needs `capabilities_service.pb.h` (the plain protobuf messages), never the `.grpc.pb.h` service stub, since HTTP doesn't ride gRPC at all.
- **Originally verified end-to-end in two pieces, not one, because of a pre-existing, unrelated environment gap**: `third_party/asio` was missing several headers (confirmed via `git stash` against a clean checkout — this predated message-versioning entirely and already blocked `test_stage11_soap.py`/`test_stage12_rest.py`/`test_consumer_example.py`/`test_stage14.py` in this Docker image), so nothing that `#include`s `crow.h` compiled, including `capabilities_http.h.tmpl`'s output. At the time this was verified two ways instead: (1) the generated route + `negotiate()` compiling and linking against a **local `crow.h` stub** covering just the API surface used, isolating the logic from the asio gap; (2) `negotiate()`'s actual networking + JSON parsing verified for real against a real Python `http.server` (success path) and a real closed port (legacy-peer path). **Resolved 2026-08-23** (see `NEXT_SESSION.md`'s resolved note) by re-vendoring the missing `asio` headers — `tests/test_message_versioning_capability_http.py`'s two Crow-server tests now pass for real against the actual generated Crow route, no code change needed here, exactly as predicted.
