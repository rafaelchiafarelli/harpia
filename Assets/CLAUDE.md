# Assets — CMake / proto / C++ templates copied into the generated build

**Role:** Static scaffolding (not generated) that the pipeline copies into the output build tree to make it compilable. Consumed by `Util/util.py` copy helpers, invoked from `main.py` (and `UnitTests/run_pipeline.py`) after code generation.

## Contents
- `CMakeLists.txt` — root of the generated project. `add_subdirectory(client|server|proto)`, C++17. Opt-in `UnitTests/` via `-DHARPIA_BUILD_TESTS=ON` (Stage 14 generated unit tests). Opt-in `-DUSE_ZMQ_CURVE=ON` (default OFF) generates ephemeral CURVE keypairs at configure time -- see gotcha below. `find_package(Doxygen QUIET)` + (when found) an always-available `doxygen` target (Foundation F6) -- see gotcha below.
- `Doxyfile` — Doxygen config (Foundation F6), copied verbatim to `<dest>/Doxyfile` by `Util.util.copyDoxygenFiles`. Small, explicit config (not the ~3000-line default template): `INPUT = USAGE_EXCERPT.md generated/cpp client server`, `USE_MDFILE_AS_MAINPAGE = USAGE_EXCERPT.md`, `WARN_IF_UNDOCUMENTED = YES`. `USAGE_EXCERPT.md` itself is NOT copied from here -- it's assembled fresh every run by `Doxygen/mainpage.py` from slices of the repo's own `USAGE.md` (§4/§6/§11), so that narrative can't drift out of sync the way a static hand-copied duplicate could.
- `cmake/curve_keygen_probe.cpp` — tiny C++ source, compiled+run via `try_run` from the root `CMakeLists.txt` when `USE_ZMQ_CURVE` is on. Calls `zmq_curve_keypair()` twice (server, client) and prints the Z85 keypairs to stdout for the root to parse. Not part of the generated project itself; copied to `<dest>/cmake/curve_keygen_probe.cpp` by `copyCMakeFiles` (same treatment as `CMakeLists.txt`/`vcpkg.json`) so `try_run`'s relative source path resolves in the generated output tree, not just in this source repo.
- `vcpkg.json` — Windows-only manifest (`protobuf`, `grpc`, `zeromq` with `curve`+`sodium` features, `cppzmq`, `soci[sqlite3,postgresql]`), copied to `<dest>/vcpkg.json` by `copyCMakeFiles` alongside the root CMakeLists so vcpkg's toolchain-file manifest mode auto-detects it. Unused on the apt-based Linux/Docker path (apt's libzmq3-dev is already libsodium-backed and CURVE-capable, confirmed via `zmq_has("curve")` -- no apt-side change needed). The `postgresql` feature is build- and live-session-verified on Windows (see `USAGE.md` §8/§12): unlike `SOCI::SQLite3`, `SOCI::PostgreSQL` needs no hand-written alias -- vcpkg's `libpq` port ships a `vcpkg-cmake-wrapper.cmake` that hooks CMake's builtin `find_package(PostgreSQL)` and defines `PostgreSQL::PostgreSQL` directly. `HarpiaTest/app_example/consumer/vcpkg.json` now also requests `soci[sqlite3,postgresql]`; its CMakeLists gains a `USE_POSTGRES` option (default OFF, so the SQLite demo is unchanged) that calls `find_package(PostgreSQL REQUIRED)` and defines `HARPIA_DEMO_POSTGRES`, which `main.cpp` uses to open a `soci::postgresql` session from a `HARPIA_PG_CONNINFO` env var instead of its default `soci::sqlite3` in-memory one.
- `proto/CMakeLists.txt` — builds the `protofiles` library; globs `protofiles/*.proto`, runs `protobuf_generate` for cpp + grpc. Tries Protobuf CONFIG then falls back to MODULE (Debian/Ubuntu apt).
- `proto/protofiles/errorCode.proto`, `heartBeat.proto` — framework standard messages, copied verbatim by `copyBasicProtos`. Carry `option java_multiple_files = true;` + `option java_package = "com.harpia.generated";` since session J.3 (`Initiatives/multi-language-targets/thread-1-java-target`) — harmless for the C++ target (ignored FileOptions), needed so `GradleAdapter` can wire them into the Java target's gRPC stub build alongside the per-message `_service.proto` that imports them.
- `proto/protofiles/capabilities_service.proto` — the S5 gRPC capability handshake's fixed wire contract (`capabilities_Request`/`capabilities_Response`/`capabilities_Service`, see `GrpcCapabilityAdapter/CLAUDE.md`), copied verbatim by `copyBasicProtos` alongside `errorCode.proto`/`heartBeat.proto`. Unlike the per-message `Service.proto` template below, this one has a `service` block of its own and needs no substitution — the contract doesn't depend on the schema, only the *server implementation* (`GrpcCapabilityAdapter`, generated) does.
- `proto/protofiles/Service.proto` — NOT copied verbatim; it is a template with `%USER_MESSAGE%` / `%USER_MESSAGE_FILE_NAME%` placeholders, read via `util.readFromTemplate` / filled by `ProtoFile/FileCreator.py`. Defines the gRPC service (heartBeat, streamSrc, pullByID, push). Also carries the same two `java_*` options as `errorCode.proto`/`heartBeat.proto` above (added in J.3) — since every filled-in `<name>_<hash>_service.proto` shares the java_package with every other message's `.proto`/`_service.proto`, its generated class names must stay unique across the whole set, which they already are (every message/type name in this template is `%USER_MESSAGE%`-prefixed).
- `server_template/` and `client_template/` — each has `CMakeLists.txt` + `src/main.cpp`. End-to-end ZMQ demo (server=PULL, client=PUSH) that exercises the generated json/ and zmq/ adapters.

## Key facts / gotchas
- Copy flow (see `Util/util.py`), dest = `HARPIA_OUTPUT_DIR` (default `./HarpiaTest/test_build`):
  - `copyBasicProtos` -> `<dest>/proto/protofiles/{errorCode,heartBeat,capabilities_service}.proto`
  - `copyCMakeFiles` -> root `CMakeLists.txt`, `<dest>/vcpkg.json`, `<dest>/cmake/curve_keygen_probe.cpp`, `<dest>/proto/`, `<dest>/server/`, `<dest>/client/` CMakeLists
  - `copyServerClientTemplates` -> `<dest>/{server,client}/src/main.cpp` via `_emitTemplate`
  - `copyDoxygenFiles` -> `<dest>/Doxyfile`; `Doxygen.mainpage.write_mainpage` (called separately, not a `copy*` helper since it assembles content rather than copying a static file) -> `<dest>/USAGE_EXCERPT.md`
- `main.cpp` placeholders `%DEMO_MESSAGE%`, `%DEMO_HASH%`, `%DEMO_SAMPLE_JSON%` are substituted by `_emitTemplate` from the demo dict (`chooseDemo` picks first push/pull message). If there is no push/pull message, `_emitTemplate` writes a trivial compiling stub instead.
- Server/client CMake include `${CMAKE_SOURCE_DIR}/generated/cpp` (harpia-generated json/zmq adapters) and link `protofiles` + `zmq` on Linux.
- **`-DUSE_ZMQ_CURVE=ON`** (see `USAGE.md` §10, `ZmqAdapter/CLAUDE.md`): the root `CMakeLists.txt` runs `cmake/curve_keygen_probe.cpp` via `try_run` at configure time (no CLI keygen tool ships with apt's `libzmq3-dev`) and writes the resulting Z85 keys into a generated `harpia_zmq_curve_keys.h` (`file(WRITE ...)`), which `server_template`/`client_template` add to their include path and `#include` when `HARPIA_DEMO_CURVE` is defined. **Do NOT pass Z85 key values through `target_compile_definitions`** — Z85's alphabet includes `# $ % ( ) [ ] { } ...`, and the underlying build-system generator (e.g. GNU Make, where `#` starts a comment and `$` triggers variable expansion) silently mangles them on the command line, producing `-D` flags that either vanish or resolve to the wrong value with no error. Hit this for real during development: three of the four keys embedded via `target_compile_definitions` on the client target simply never reached the compiler (`error: 'HARPIA_ZMQ_CURVE_SERVER_PUBLIC' was not declared`) despite the CMake-side value being correct — only visible by actually building, not by inspecting the generated `CMakeLists.txt` text (which looked fine). A generated header sidesteps the shell/Make layer entirely.
- **Windows (verified, see `USAGE.md` §12):** server/client CMakeLists branch on `if(WIN32)` — link `cppzmq` (vcpkg CONFIG target) instead of bare `zmq`, and list `${CMAKE_BINARY_DIR}/proto` *ahead of* `generated/cpp` on the include path so the adapter headers' `#include "protofiles/...pb.h"` resolves to `proto/CMakeLists.txt`'s freshly vcpkg-protoc-regenerated copy instead of the Docker-baked one (a protobuf version mismatch otherwise fails to compile — Google has removed/moved internal headers like `map_field_inl.h` across major versions). The Linux branch is untouched. `-DUSE_ZMQ_CURVE=ON` is not yet build-verified on Windows (vcpkg's `zeromq` port needs its `curve`+`sodium` features, already added to `vcpkg.json`; the `try_run` probe there needs `find_package(ZeroMQ CONFIG)`'s `libzmq` target, not a bare `find_library`, same gotcha as the demo targets themselves).
- **`doxygen` CMake target (Foundation F6):** `find_package(Doxygen QUIET)` -- when absent, the target simply doesn't exist (not a configure error), same "optional tool, non-fatal when missing" convention as `ProtoCompiler`/`GrpcCompiler` on the Python side. `OUTPUT_DIRECTORY = docs/doxygen` in the Doxyfile is two path components deep; Doxygen only auto-creates one missing level and errors on the rest (hit this during development: `error: tag OUTPUT_DIRECTORY: Output directory 'docs/doxygen' does not exist and cannot be created`), so the custom target runs `${CMAKE_COMMAND} -E make_directory` first. `cmake --build . --target doxygen` -> `docs/doxygen/html/index.html`, mainpage from `USAGE_EXCERPT.md`.
- **F6 does not assert "zero warnings" against this real generated project.** None of the current templates/runtime headers use actual Doxygen comment syntax yet (`///`/`/** */` -- plain `//` prose doesn't count for `WARN_IF_UNDOCUMENTED`), because writing those is explicitly Ground Rule 6's job (per-track, ongoing), not F6's ("one-time plumbing" only). `UnitTests/test_doxygen_docs.py` proves the `WARN_IF_UNDOCUMENTED=YES` mechanism itself is real (catches an undocumented class, stays clean on a documented one) against a tiny synthetic fixture, and proves the actual CMake target builds real HTML end-to-end against the real generated project -- but doesn't require today's undocumented headers to already comply, which was never this task's job.
- These are hand-maintained source templates — edit here to change generated-project scaffolding; do not edit copies under `test_build/` (regenerated/gitignored).
