# Assets — CMake / proto / C++ templates copied into the generated build

**Role:** Static scaffolding (not generated) that the pipeline copies into the output build tree to make it compilable. Consumed by `Util/util.py` copy helpers, invoked from `main.py` (and `tests/run_pipeline.py`) after code generation.

## Contents
- `CMakeLists.txt` — root of the generated project. `add_subdirectory(client|server|proto)`, C++17. Opt-in `tests/` via `-DHARPIA_BUILD_TESTS=ON` (Stage 14 generated unit tests). Opt-in `-DUSE_ZMQ_CURVE=ON` (default OFF) generates ephemeral CURVE keypairs at configure time -- see gotcha below.
- `cmake/curve_keygen_probe.cpp` — tiny C++ source, compiled+run via `try_run` from the root `CMakeLists.txt` when `USE_ZMQ_CURVE` is on. Calls `zmq_curve_keypair()` twice (server, client) and prints the Z85 keypairs to stdout for the root to parse. Not part of the generated project itself; copied to `<dest>/cmake/curve_keygen_probe.cpp` by `copyCMakeFiles` (same treatment as `CMakeLists.txt`/`vcpkg.json`) so `try_run`'s relative source path resolves in the generated output tree, not just in this source repo.
- `vcpkg.json` — Windows-only manifest (`protobuf`, `grpc`, `zeromq` with `curve`+`sodium` features, `cppzmq`, `soci[sqlite3,postgresql]`), copied to `<dest>/vcpkg.json` by `copyCMakeFiles` alongside the root CMakeLists so vcpkg's toolchain-file manifest mode auto-detects it. Unused on the apt-based Linux/Docker path (apt's libzmq3-dev is already libsodium-backed and CURVE-capable, confirmed via `zmq_has("curve")` -- no apt-side change needed). The `postgresql` feature is requested but not yet build-verified on Windows (see `USAGE.md` §12's known gaps) -- `examples/consumer/vcpkg.json` deliberately stays `soci[sqlite3]`-only since that demo's `main.cpp` hardcodes a sqlite3 in-memory session.
- `proto/CMakeLists.txt` — builds the `protofiles` library; globs `protofiles/*.proto`, runs `protobuf_generate` for cpp + grpc. Tries Protobuf CONFIG then falls back to MODULE (Debian/Ubuntu apt).
- `proto/protofiles/errorCode.proto`, `heartBeat.proto` — framework standard messages, copied verbatim by `copyBasicProtos`.
- `proto/protofiles/Service.proto` — NOT copied verbatim; it is a template with `%USER_MESSAGE%` / `%USER_MESSAGE_FILE_NAME%` placeholders, read via `util.readFromTemplate` / filled by `ProtoFile/FileCreator.py`. Defines the gRPC service (heartBeat, streamSrc, pullByID, push).
- `server_template/` and `client_template/` — each has `CMakeLists.txt` + `src/main.cpp`. End-to-end ZMQ demo (server=PULL, client=PUSH) that exercises the generated json/ and zmq/ adapters.

## Key facts / gotchas
- Copy flow (see `Util/util.py`), dest = `HARPIA_OUTPUT_DIR` (default `./HarpiaTest/test_build`):
  - `copyBasicProtos` -> `<dest>/proto/protofiles/{errorCode,heartBeat}.proto`
  - `copyCMakeFiles` -> root `CMakeLists.txt`, `<dest>/vcpkg.json`, `<dest>/cmake/curve_keygen_probe.cpp`, `<dest>/proto/`, `<dest>/server/`, `<dest>/client/` CMakeLists
  - `copyServerClientTemplates` -> `<dest>/{server,client}/src/main.cpp` via `_emitTemplate`
- `main.cpp` placeholders `%DEMO_MESSAGE%`, `%DEMO_HASH%`, `%DEMO_SAMPLE_JSON%` are substituted by `_emitTemplate` from the demo dict (`chooseDemo` picks first push/pull message). If there is no push/pull message, `_emitTemplate` writes a trivial compiling stub instead.
- Server/client CMake include `${CMAKE_SOURCE_DIR}/generated/cpp` (harpia-generated json/zmq adapters) and link `protofiles` + `zmq` on Linux.
- **`-DUSE_ZMQ_CURVE=ON`** (see `USAGE.md` §10, `ZmqAdapter/CLAUDE.md`): the root `CMakeLists.txt` runs `cmake/curve_keygen_probe.cpp` via `try_run` at configure time (no CLI keygen tool ships with apt's `libzmq3-dev`) and writes the resulting Z85 keys into a generated `harpia_zmq_curve_keys.h` (`file(WRITE ...)`), which `server_template`/`client_template` add to their include path and `#include` when `HARPIA_DEMO_CURVE` is defined. **Do NOT pass Z85 key values through `target_compile_definitions`** — Z85's alphabet includes `# $ % ( ) [ ] { } ...`, and the underlying build-system generator (e.g. GNU Make, where `#` starts a comment and `$` triggers variable expansion) silently mangles them on the command line, producing `-D` flags that either vanish or resolve to the wrong value with no error. Hit this for real during development: three of the four keys embedded via `target_compile_definitions` on the client target simply never reached the compiler (`error: 'HARPIA_ZMQ_CURVE_SERVER_PUBLIC' was not declared`) despite the CMake-side value being correct — only visible by actually building, not by inspecting the generated `CMakeLists.txt` text (which looked fine). A generated header sidesteps the shell/Make layer entirely.
- **Windows (verified, see `USAGE.md` §12):** server/client CMakeLists branch on `if(WIN32)` — link `cppzmq` (vcpkg CONFIG target) instead of bare `zmq`, and list `${CMAKE_BINARY_DIR}/proto` *ahead of* `generated/cpp` on the include path so the adapter headers' `#include "protofiles/...pb.h"` resolves to `proto/CMakeLists.txt`'s freshly vcpkg-protoc-regenerated copy instead of the Docker-baked one (a protobuf version mismatch otherwise fails to compile — Google has removed/moved internal headers like `map_field_inl.h` across major versions). The Linux branch is untouched. `-DUSE_ZMQ_CURVE=ON` is not yet build-verified on Windows (vcpkg's `zeromq` port needs its `curve`+`sodium` features, already added to `vcpkg.json`; the `try_run` probe there needs `find_package(ZeroMQ CONFIG)`'s `libzmq` target, not a bare `find_library`, same gotcha as the demo targets themselves).
- These are hand-maintained source templates — edit here to change generated-project scaffolding; do not edit copies under `test_build/` (regenerated/gitignored).
