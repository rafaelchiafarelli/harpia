# Database — Stage 8/11/12/13 back-end: SQL schema, CRUDL DAOs, migrations, DB<->JSON/XML io, REST, SOAP, WSDL, gRPC impls

**Pipeline role:** Stage 8 (SQL schema, CRUDL, migrations, DbIo) + Stage 11 (SOAP, WSDL) + Stage 12 (REST) + Stage 13 (gRPC service impl). Everything is generated from the `Message` objects produced upstream (LexicalAnalizer/MessageCreator).
**Entry points:** every adapter has the same shape `XxxAdapter(messages=msgFactory.messages, dest=testDestination).Process()`; called from `main.py`. `Process()` returns `None` (logs a count; not a real error object). Constructors take only `(messages, dest)`.
**Inputs → Outputs:** consume the full `messages` list (each `Message` has `.name`, `.md5Hash`, `.tableName`, `.visibility`, `.isEnum`, `.variables`; each variable has `.name`, `.type` (a `[kind, refName]` pair — `"ID"` means composed ref), `.modifiers`, `.typeMap`). Every adapter skips enums and messages with no `tableName` (SqlAdapter emits a one-line note instead). Output roots under `<dest>`:
  - SqlAdapter → `<dest>/database/` (`.sql`)
  - WsdlAdapter → `<dest>/wsdl/` (`.wsdl`)
  - all C++ header adapters → `<dest>/generated/cpp/<sub>/` where `<sub>` = `db`, `migrate`, `dbio`, `rest`, `soap`, `grpc`

## Files
- `model.py` — **the shared schema model; central, read first.** `type_registry(messages)` maps each declared type name → `{"kind": "enum"|"table"|"message", "msg": <Message>}` (table = has `tableName`, message = composed but table-less). `analyze(msg, types)` → `(columns, notes)`: scalar field → bindable `Column` (SQLite type via `_SCALARS`; `ID_*` → INTEGER PRIMARY KEY; `REQUIRED`→NOT NULL, `UNIQUE`→UNIQUE); composed field to an **enum** → bindable INTEGER column; to a **table** message → non-bindable `fk_table` INTEGER column holding the child's PK; to a **table-less** message → `_flatten()` inlines its scalar/enum sub-fields as prefixed columns `parent_sub` bound through the parent accessor chain (`Column.embed` is a LIST of accessors, e.g. `["path","start"]` for 2-level nesting; `child_accessor` is the final step; C++ `x.path().start().city()`). `_flatten()` recurses when a sub-field is itself composed to ANOTHER table-less message, compounding the column-name prefix and the embed chain (`prefix=False` skips both, for one repetition's worth of unprefixed/unbound columns — see `RepeatedComposedField` below). Map fields are deferred here (emit a `note`) and handled by `map_fields()`; repeated fields likewise by `repeated_fields()`. `Column` carries C++ codegen helpers: `getter()`, `set_stmt()`, `sql_def()`. `MapField` → child table `<table>__<field>` (owner, key, value); `RepeatedField` → child table `<table>__<field>` (owner, ordinal, value), with `fk_target` set when it's a repeated composed→table field (1-to-many via link table storing the child PK); `RepeatedComposedField` → child table `<table>__<field>` (owner, ordinal, one column per the target's own flattened scalar/enum fields, unprefixed) when the repeated field's target has no table of its own. All three support embed-nested variants (map/repeated/repeated-composed reached through a flattened table-less composed field, table name `<table>__<embed>_<field>`) — that embed stays a single-level string (only `_flatten()`'s own `embed_path` is a multi-level chain). `RepeatedField` and `MapField` also carry `renamed_from` (from the field's `renamed_from[<old>]` modifier) so MigrationAdapter can rename the whole `<table>__<old>` child table. `Column.is_phi` (from `variable.is_phi`, Foundation F2) tags a bindable scalar/enum column whose value CrudlAdapter envelope-encrypts (the db-encryption epic). `_HIDDEN_PREFIXES` (ID_/STATUS_/ERROR_/ORIGINATOR) are front-end-injected fields skipped when flattening. `create_table_sql()` = compact one-line CREATE TABLE for embedding in C++. `child_table_names(msg)` = every child-table name (`map_fields` + `repeated_fields`, all variants) the current schema declares — MigrationAdapter's orphan-reap diff target. `pagination_default(msg)` → the `paginationSize` of the first field carrying the `PAGINATION` modifier, or `None`; drives the paginated `list(offset, limit)` DAO overload's REST default.
- `SqlAdapter.py` — Stage 8 schema. Renders `templates/table.sql.tmpl` per message → `<name>_<hash>_table.sql`. Emits the main CREATE TABLE plus one child table per map (owner,key,value) and per repeated scalar (owner,ordinal,value). Validated against vendored SQLite in tests.
- `CrudlAdapter.py` — **largest/most important.** Header-only DAO `<name>_<hash>_crudl.h` (`::harpia::db::<name>_dao`) over vendored sqlite3: create/read/update/remove/list (+ a paginated `list(out, offset, limit)` overload, `LIMIT`/`OFFSET` bound via SOCI) + create_table/drop_table. Builds INSERT/SELECT/UPDATE bind & extract lines from `analyze()` columns so SQL matches the schema. Handles: scalar/enum, flattened-embed columns (incl. multi-level nested embed chains), singular FK-to-table columns (child persisted/loaded via the child's own DAO — `_fk_hooks`/`_fk_extract`), map child tables, repeated-scalar child tables, repeated-FK link tables (1-to-many, persists each child via its DAO then links its PK, `_rep_write`/`_rep_read`), and repeated-composed-to-table-less child tables (`_rep_composed_write`/`_rep_composed_read`, one multi-column row per element, no child DAO). Pulls in child-DAO headers via `_fk_includes`. Includes the message's protobuf header `protofiles/<name>_<hash>.pb.h`. **`phi` columns (the db-encryption epic):** when a message has a `Column.is_phi` field, the DAO gains a `::harpia::crypto::KeyProvider& kp_` member + a defaulted ctor param (`= ::harpia::crypto::default_key_provider()`), `#include "crypto/harpia_encrypted_column.h"`, and its create/update bind locals wrap the value in `encrypt_field(kp_, …)` (numeric/enum stringified first) while the read/list extract path reads the column as text and runs `decrypt_field[_ll|_int|_double](kp_, …)` — ciphertext is marker+hex so it stays in the column's existing type. `Process()` copies the crypto runtime into `generated/cpp/crypto/` (via `Crypto.key_provider_common`): `harpia_encrypted_column.h` + the key-management task 1 interface + `harpia_audit_sink.h` (db-encryption task 1), plus the `LocalKeyProvider` / `KmsKeyProvider` backend headers (db-encryption task 2, so a deployment can pass the DAO a real persistent provider — the ctor param already accepts one). A `phi`-bearing DAO also holds an `::harpia::compliance::AuditSink&` (defaulted ctor param, after `kp_`) and emits exactly one `audit_.record("phi_<op>", "<table>", "<phi col names>")` per CRUDL op (`phi_create`/`phi_read`/`phi_update`/`phi_delete`/`phi_list`) — names only, never a value (Rule 5); a not-found `read` audits nothing (db-encryption task 3). Messages with no `phi` column emit byte-identical output. **`event` messages (events-callbacks epic task 1):** when a message carries the `event` modifier (`Callback.callback_common.is_event_message`), the DAO `#include`s `events/<name>_<hash>_events.h` and calls `::harpia::events::<name>_channel().publish(msg);` at the end of a successful `create()` and `update()` (the OnChange points) — **never** in `read`/`list`/`remove`. Same empty-placeholder technique as the `phi` audit hook, so a non-`event` DAO is byte-identical; the `events/` header + `harpia_event_cache.h` runtime are emitted by `Callback/CallbackAdapter.py`, not copied here. A table-less `event` message has no DAO, so its channel is application-published. **`event` + `phi` (events-callbacks epic task 3):** a message that is *both* also emits one extra `audit_.record("phi_event_onchange", "<table>", "<phi cols>")` right after the `publish(msg)` call in `create()`/`update()` — "a persisted phi change reached the event bus", distinct from the channel's own `phi_event_dispatch`. Reuses the existing `audit_` member; a non-phi event DAO and a phi non-event DAO are byte-identical.
- `DbRegistryAdapter.py` — **Stage 8, public/private DB segregation (the db-segregation epic).** Unlike every other adapter here it emits **one project-wide file**, `generated/cpp/db/harpia_db_registry.h`, not one per message. It is the *environment-level registry*: a `constexpr std::array<RegistryEntry>` of `{tableName, Visibility::PUBLIC|PRIVATE, owner_project}` for every table-bearing message (enums / table-less messages skipped), deduped by table name (first declaration wins; a differing later declaration for the same name — `users` PUBLIC vs `top_users` PRIVATE both → `user_table` in the fixture — is emitted as a `// note:` line above the array, not silently dropped, and not "fixed" here). `owner_project` / `kProjectName` come from `ComplianceContext.project` (`project.harpia.yaml` → `project:`, default `"default"`). Also emits the check the registry exists for: `harpia::db::db_access_check(requesting_project, target_table)` → `AccessDecision::{ALLOWED, DENIED_PRIVATE_CROSS_PROJECT, DENIED_UNKNOWN_TABLE}` (unknown table → denied; PUBLIC → always allowed; PRIVATE → allowed iff `requesting_project == owner_project`) plus a one-arg overload keyed off `kProjectName`. Header-only / `constexpr` (even `static_assert`-usable) and self-contained, so a *second* generated project `#include`s this project's registry directly and passes its own name to ask "am I allowed at their table?". **Purely additive** — no per-message SQL/DAO/proto output changes, so a single-project build is byte-for-byte unaffected; the golden snapshot only gains `db/harpia_db_registry.h`. Runs in `main.py` right after `CrudlAdapter`.
- `MigrationAdapter.py` — Stage 8 migration. `<name>_<hash>_migrate.h` with `migrate_<name>(sqlite3*)`. Ensures table (+child tables) exist; RENAMEs a column carrying the DSL's `renamed_from[<old>]` modifier (both names known at generation time, so this runs first and corrects the runtime `have` set before add/drop see it); `ALTER TABLE ADD COLUMN` for any non-PK column an older version lacks; then an optional caller-supplied `data_transform` hook (`std::function<void(session&)>`, defaults to a no-op) for cross-version **value** transforms — see below; DROPs any live column the current schema no longer declares (an inverse diff against the runtime-introspected column set — implicit/unconditional, since there is no schema history to distinguish "intentionally removed" from "stray"); RETYPEs any column whose live SQL type no longer matches the current schema for that name — runs last (after rename/add/drop have stabilized the column set), detected by a second runtime introspection pass into a `have_types` map; unlike rename this needs no DSL modifier since the name is unchanged, so a mismatch is unambiguous (`DbBackend.retype_column_dynamic`: Postgres fixes each column independently via a direct `ALTER COLUMN ... TYPE`; SQLite has none, so it rebuilds the whole table — create with the current schema, `INSERT ... SELECT CAST(...)` every row across, drop the old table, rename the new one into place); records version in `_harpia_schema_version`. **Child tables (repeated/map `<table>__*`) get the same rename/drop/retype treatment (`repeated_fields()` + `map_fields()`-driven; the schema-evolution epic.1 = repeated-scalar, schema-evolution task 2 = map, schema-evolution task 3 = repeated-composed):** a repeated/map field carrying `renamed_from[<old>]` moves its `<table>__<old>` child table to `<table>__<new>` *before* `create_table()`'s `CREATE IF NOT EXISTS` would leave an empty new one beside the populated old (`DbBackend.rename_table`; direct fields only — an embed-nested field's `renamed_from` is not plumbed); after the main table is stabilized, any live `<table>__*` table the current schema no longer declares (`model.child_table_names()` is the full current set — map + repeated-scalar + repeated-FK + repeated-composed + embed-nested) is reaped (`DbBackend.drop_table_dynamic`, same implicit no-schema-history diff as the column drop, keyed off a `list_tables_sql(prefix)` introspection into `_child_have`); and each surviving child table's own columns are brought to the current shape: a repeated-scalar `value` column (`DbBackend.retype_rep_child_dynamic`), a map `key`/`value` column (`DbBackend.retype_map_child_dynamic`), or — for a repeated-composed child table, whose data columns are one-per-target-field and evolve independently — the full ADD/DROP/RETYPE of those columns (`DbBackend.evolve_rep_composed_child_dynamic`: `owner`/`ordinal` always kept; Postgres `ALTER COLUMN` per column, SQLite ADDs missing columns then rebuilds `(owner, ordinal, <current data cols>)` with a `CAST`, which also drops strays). Emitted in *every* `migrate.h` (the orphan-reap scan runs even for a message with no child tables, so a version that dropped its last repeated/map field still gets cleaned up). **`data_transform` hook (template-only change, `_render()` untouched):** deriving one column's value from another (e.g. `age` from `birthdate`, or splitting a retiring `full_name` into `first_name`/`last_name`) can't be expressed by an automatic structural diff — harpia has no schema history, so it doesn't know what a transform should *compute*, only guarantee a stable extension point and when it runs. Deliberately NOT new DSL syntax (`renamed_from`-style): the DSL's flat, non-recursive grammar can't host arbitrary transform logic, so the caller supplies a lambda instead, same "harpia wires the capability, caller supplies the logic" precedent as TLS/CURVE. **Ordering matters**: the hook runs after ADD (so a new destination column already exists to write into) and before DROP (so an old source column being retired is still there to read) — reversing this breaks the split-column case specifically, since the source data would already be gone. See `USAGE.md` §6.
- `DbIoAdapter.py` — Stage 8/9/10 bulk io. `<name>_<hash>_dbio.h` composing the CRUDL DAO with the JSON and XML adapters: `export_json`/`import_json` (newline-delimited JSON) and `export_xml`/`import_xml` (`<name>_list` wrapper). Pure template fill (name/hash only).
- `RestAdapter.py` — Stage 12. `<name>_<hash>_rest.h`: registers CRUD routes on a Crow server (`crow::SimpleApp`, via `route_dynamic`) backed by the DAO. GET-list is paginated via `?limit=&offset=` (limit>0 triggers the DAO's paginated overload; the message's `pagination_default()` becomes the default limit when the request omits it). Content negotiation (XML if Content-Type/Accept says "xml", else JSON) reusing JSON+XML adapters. Credential-gated (see gotchas). Template-only fill except `default_limit` (from `pagination_default()`).
- `SoapAdapter.py` — Stage 11. `<name>_<hash>_soap.h`: SOAP envelope endpoint on a Crow server (`crow::SimpleApp`) (get/set/update/delete in Body) using tinyxml2 + XML adapter + DAO. Template-only.
- `WsdlAdapter.py` — Stage 11. Static `<name>_<hash>.wsdl` (WSDL 1.1, document/literal SOAP 1.1) describing the SOAP service. complexType lists only top-level **bindable** scalar/enum fields (via `analyze()` + `_XSD` kind→XSD map); nested/repeated/map handled by the runtime, not expanded. No C++.
- `GrpcServiceAdapter.py` — Stage 13. `<name>_<hash>_grpc.h`: concrete impl of the service skeleton emitted by ProtoFile/GrpcCompiler; RPCs call the DAO (push→create, pullByID→read, streamSrc→list [paginated via the request's `offset`/`limit` fields when `limit>0`, else unbounded], heartBeat→echo). Data RPCs credential-gated via call metadata. Per-message output is template-only. **Also emits a project-wide gRPC server bring-up whenever ≥1 table message exists (transport-authn task 2, mtls-grpc):** `grpc/harpia_grpc_mtls.h` (hand-written, copied verbatim from `Database/runtime/` — `harpia::grpc_transport::{MtlsFiles, SecurityRefused, server_credentials, channel_credentials}`, fail-safe: `hardening_required` + incomplete PEM paths → throws, never a silent insecure downgrade); `grpc/grpc_server_bringup.h` (rendered from `templates/grpc_server_bringup.h.tmpl` — `#include`s every `<name>_grpc.h`, bakes `kHardeningRequired` from `Crypto.backend.transport_hardening_required(compliance)`, defines the `GrpcServer` class that registers all services + picks mTLS/insecure `ServerCredentials`); `grpc/grpc_server_selection.json` (F5 CryptoBackend choice + hardening flag, same field set as `dds_security_selection.json`). Takes `crypto_backend=` like DdsAdapter. Path constants in `Compliance/grpc_common.py`.
- `templates/` — one template per adapter, filled with `str.format` (literal C++ braces are `{{`/`}}`): `table.sql.tmpl`, `crudl.h.tmpl`, `migrate.h.tmpl`, `dbio.h.tmpl`, `rest.h.tmpl`, `soap.h.tmpl`, `grpc_service.h.tmpl` (all C++/SQL), and `wsdl.tmpl` (XML). Loaded once at import via `Util.util.loadTemplate(__file__, name)`.

## Key facts / gotchas
- **Output filenames are md5-hash-qualified: `<name>_<md5Hash>_<suffix>`** (`_table.sql`, `_crudl.h`, `_migrate.h`, `_dbio.h`, `_rest.h`, `_soap.h`, `_grpc.h`, `.wsdl`). Include-guards and pb-header refs also embed `<name>_<hash>`. Relevant to the upcoming multi-root feature: the hash disambiguates same-named messages, but only where the hash is applied — filenames and guards are safe.
- **SQL/C++ identifiers are NOT hash-qualified:** `tableName`, child-table names (`<table>__<field>`), the C++ `<name>_dao` class, `authorized_<name>`, and (per the sibling ProtoFile stage) **service proto MESSAGE names** are plain `name` — a dup-def / collision risk across roots that the multi-root work must address.
- **Credential/auth is currently the message name + hash as literals, not a real Stage 5 credential:** REST checks `X-User == "<name>" && X-Pswd == "<hash>"` (401 otherwise); SOAP gates the same way; gRPC checks `x-user`/`x-pswd` call metadata (UNAUTHENTICATED on mismatch). heartBeat/gRPC stays open. So the "access credential" baked in is just `{name}`/`{hash}`.
- **TLS is caller-side for REST/SOAP, generated for gRPC.** RestAdapter/SoapAdapter still never generate the `crow::SimpleApp` server-construction call — it was always caller code (`app.port().run()`; the vendored `third_party/crow/crow.h` already supports `CROW_ENABLE_SSL`/`ssl_file()`); see `USAGE.md` §9 and `HarpiaTest/app_example/consumer -DUSE_TLS=ON`. **gRPC changed with transport-authn task 2 (mtls-grpc):** GrpcServiceAdapter now *does* emit a project-wide server bring-up — `grpc/grpc_server_bringup.h`'s `harpia::grpc_transport::GrpcServer` registers every generated service on a `ServerBuilder` and calls `BuildAndStart()` with mTLS-or-insecure credentials chosen by `transport_hardening_required(compliance)` at generation time (fail-safe `harpia_grpc_mtls.h` helper, copied verbatim; `grpc_server_selection.json` records the F5 choice). `mtls-rest-soap` (task 3) is expected to do the equivalent for the Crow side.
- **`rest.h.tmpl`/`soap.h.tmpl` on Windows (verified, see `USAGE.md` §11):** both force `#include <windows.h>` + `#undef DELETE` *before* `#include "crow.h"`. Crow's `HTTPMethod` enum guards its ALL-CAPS members (`GET`/`POST`/`PUT`/`DELETE`/...) with a single `#ifndef DELETE`, but Crow's own `#include <asio.hpp>` (near its top) pulls in `<windows.h>` — which defines `DELETE` as a generic-access-rights macro — well before Crow reaches its own enum, so an undef placed merely before `#include "crow.h"` in *our* code doesn't survive that internal re-inclusion; only forcing `<windows.h>` first (so its own include guard makes Crow/asio's later `#include <windows.h>` a no-op) works. Without this, `crow::HTTPMethod::GET` etc. silently stop existing (Crow falls back to TitleCase-only members) and every generated route registration fails to compile.
- FK/map/repeated/embed persistence design lives entirely in `model.py`; SqlAdapter, CrudlAdapter, MigrationAdapter, WsdlAdapter all re-derive columns from `analyze()` (+`map_fields`/`repeated_fields`) so schema, DAO SQL, migration and WSDL never drift. RestAdapter/SoapAdapter/DbIoAdapter/GrpcServiceAdapter do NOT call `analyze()` — they only substitute name/hash and delegate to the DAO + JSON/XML adapters at C++ level.
- Structural migration (rename/add/drop/type-change) is fully implemented for the main table *and* for child tables — repeated-scalar (the schema-evolution epic.1), map (schema-evolution task 2), and repeated-composed (schema-evolution task 3, whose per-target-field data columns evolve independently); see the `MigrationAdapter.py` bullet — plus an optional `data_transform` hook for value-level transforms (see the `MigrationAdapter.py` bullet above) — this closes what was previously the last unscoped Known-gaps item on the migration side. (Repeated fields whose target is table-less, composed fields nested inside an embedded message whose own target is ALSO table-less, and composed fields nested inside an embedded message whose OWN target is a table-bearing message — an FK found inside an embed, via `_flatten()`'s `kind == "table"` branch and `Column.mutable_ptr()`/`has_expr()` in `CrudlAdapter` — are all implemented; see `RepeatedComposedField` and `_flatten()`'s recursion above.)
- `analyze` deliberately falls back to a deferred plain-INTEGER FK when `types` is missing/unknown — always pass `self.types` (adapters do).
- **No multi-language `DbBackend`-style seam exists yet, deliberately** — this module's DB logic is still C++-specific (SOCI-backed), and the Java target's DB port (`JavaDatabase/`) is a separate, non-shared implementation, not a language-agnostic abstraction over both. One data point (C++) wasn't enough to design `Database/backends/`'s own dialect seam until Postgres gave it a second case to diff against SQLite; the same reasoning applies here — Java as a second *language* data point (chosen deliberately before Python, for Android-fleet business reasons — see `JavaDatabase/CLAUDE.md`) still isn't enough to design a cross-language seam. Wait for Python (the third language) before attempting one, or at minimum treat any two-language seam as provisional.

## Touchpoints
- Called by: `main.py` (order: GrpcServiceAdapter, then Sql, Crudl, DbRegistry, Migration, DbIo, Rest, Soap, Wsdl) and `run_pipeline.py`/`run_harpia.sh`.
- Depends on: `Database.model`; `Message` objects from `LexicalAnalizer`/`Message` (MessageCreator); `Logger.logger`, `Util.util.loadTemplate`; `Callback.callback_common.is_event_message` (CrudlAdapter, for the event publish hook); `Errors.Error` (imported by SqlAdapter but unused). Generated C++ depends on vendored sqlite3 (`third_party/sqlite`), Crow + standalone asio (`third_party/crow`, `third_party/asio`), tinyxml2, protobuf/gRPC, the sibling JSON/XML adapters' generated headers, and — for an `event` message's DAO — `generated/cpp/events/` (emitted by `Callback/CallbackAdapter.py`).
