# JavaZmqAdapter — Java target: ZMQ transport over JeroMQ (no CURVE yet — J.19)

**Pipeline role:** Java-target Stage 13 (zmq) equivalent (session J.18, `initiatives/multi-language-targets/thread-1-java-target`). `org.zeromq:jeromq` — a pure-Java ZMTP reimplementation, no JNI, no native library, no per-platform build (genuinely simpler than the C++ target's cppzmq/libzmq story, `../../README.md` §2). CURVE support confirmed for the pinned version in J.17 (`histories/ZMQ/confirm-JeroMQ-CURVE-support.md`) but NOT implemented here — that's J.19.
**Entry point (from main.py):** gated behind `HARPIA_GEN_LANG=java`, called right after `JavaSoapAdapter` in the same block: `JavaZmqAdapter(messages=msgFactory.messages, dest=testDestination, compliance=complianceContext).Process()`. Returns `None` or an `Error` (non-fatal; main.py logs it).
**Inputs → Outputs:** consumes message objects, filtered exactly like the C++ `ZmqAdapter` (skip enums; a message needs a PUSH/PULL or EVENT/STREAM access modifier or it's skipped entirely). Emits `<dest>/java/src/main/java/com/harpia/runtime/zmq/HarpiaZmq.java` (shared) and `<dest>/java/src/main/java/com/harpia/generated/zmq/<name>_zmq.java` (one per transport-bearing message).

## Files
- `runtime/HarpiaZmq.java` — hand-written (NOT generated), copied verbatim. `HarpiaZmq.Sender` (PUSH via connect, or PUB via bind — one class, a `bind` boolean picks the role) stamps the message's `ORIGINATOR` field (found by name prefix via reflection, same `FieldDescriptor`-lookup strategy as `JdbcBind`/`HarpiaXml` — no camelCase accessor guessing) before calling `Message.toByteArray()`/`Socket.send(byte[], int)`. `HarpiaZmq.Receiver` (PULL via bind, or SUB via connect+subscribe-all — same one-class-two-roles shape) calls `Socket.recv(int)`/`Message.Builder.mergeFrom(byte[])`. `runtimeOriginId()` is the Java port of the C++ runtime's `runtime_origin_id()` (pid + a per-process monotonic counter + random bits — `ProcessHandle.current().pid()` + `AtomicLong` + `SecureRandom`).
- `templates/zmq.java.tmpl` — per-message `com.harpia.generated.zmq.<name>_zmq`: a static `ORIGIN_ID` constant (the compile-time one-to-* id, reusing `ZmqAdapter.ZmqAdapter._origin_id()` **by import**, not re-derived) plus thin static factory methods (`newSender`/`newReceiver`/`newPublisher`/`newSubscriber`, only the ones the message's declared modifiers call for) that construct the shared `HarpiaZmq` classes with the right `SocketType`/bind-vs-connect/origin-id defaults — mirroring the C++ target's per-message default constructors' ergonomics without needing 4 full generated classes per message.

## Why one shared runtime class, not 4 per-message classes like C++ (the actual design decision this session made)
C++'s `ZmqAdapter` generates 4 real classes per message (`<name>_sender/_receiver/_publisher/_subscriber`) because C++ has no common base for "a protobuf message" convenient enough to write one generic sender against (`SerializeToString`/manual `zmq::message_t` byte copy, all typed to `const {cls}&`). protobuf-java's common `Message` interface plus JeroMQ's plain `byte[]` `send`/`recv` (`Message.toByteArray()`/`Message.Builder.mergeFrom(byte[])`, no manual byte copying at all) make the ENTIRE transport body generic over any message type — there's nothing left that's genuinely per-message except the small, ergonomic pieces (the compile-time origin id, and which `SocketType`/bind-vs-connect a given message's declared modifiers call for). Generating the whole 4-class shape anyway, just to mirror C++'s file layout, would be exactly the kind of boilerplate-for-parity's-sake this thread's Java-side adapters have consistently avoided since `JavaJsonAdapter` (J.4) — see that module's `CLAUDE.md` for the first, fuller version of this argument.

## Key facts / gotchas
- `_origin_id()`/`_is_one_to_many()` are **imported directly** from `ZmqAdapter.ZmqAdapter` (`from ZmqAdapter.ZmqAdapter import _origin_id, _is_one_to_many`) rather than re-implemented — the exact same deterministic-id derivation (`md5("{file_hash}:{name}")[:15]` as a decimal string) and one-to-*/many-to-* classification (PULL/EVENT/STREAM present → one-to-*) the C++ target already uses. A real, direct code reuse, not just "the same idea ported."
- The classification determines the origin-id EXPRESSION each factory method embeds: `ORIGIN_ID` (the compile-time constant) for a one-to-* message, or a fresh `HarpiaZmq.runtimeOriginId()` call for a many-to-* one — computed at each `newSender`/`newPublisher` CALL (not cached), so every constructed sender/publisher instance for a many-to-* message gets its own distinguishable id, matching the C++ target's own "default constructor computes it fresh" behavior.
- The `ORIGINATOR` field's OWN NAME varies (`ORIGINATOR_<hash>` for a one-to-* message, bare `ORIGINATOR` otherwise — `message/Variables.py`'s `AddHiddenVariables`) — irrelevant to `HarpiaZmq.Sender`, since it finds the field by name PREFIX via reflection rather than needing the exact name, let alone a derived Java accessor for it.
- `Socket.send`/`Socket.recv` are used with default (blocking) flags (`0`) — no `ZMQ.DONTWAIT`, matching the C++ runtime's own blocking `send`/`recv` calls.

## Touchpoints
- Called by: `main.py`, gated on `HARPIA_GEN_LANG=java`, right after `JavaSoapAdapter` in the same conditional block.
- Depends on: `ZmqAdapter.ZmqAdapter` (`_origin_id`, `_is_one_to_many` — a direct Python import, the one place this Java-target package depends on a C++-target package's internals rather than only `Database.model`/`Errors`/`Util`/`Logger`), `Util.util.copy_if_different`/`write_if_different`/`loadTemplate`, `Logger.logger`, `Errors.Error`. The runtime class depends on `protobuf-java` (already present) and `org.zeromq:jeromq:0.6.0` (new this session, `GradleAdapter/templates/project.gradle.tmpl`).
- Consumed by: J.19 (CURVE-secured variant — extends `HarpiaZmq.Sender`/`Receiver`'s constructors with optional CURVE key material, same shape as the C++ runtime's own `CurveServerKeys`/`CurveClientKeys` structs), J.20 (acceptance gate).
