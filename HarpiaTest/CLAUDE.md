# HarpiaTest — sample `.harpia` input + generated output tree

**Role:** The canonical demo/test input the pipeline runs on by default, plus its generated build output. `main.py` defaults: input `./HarpiaTest/test.harpia`, includes `./HarpiaTest/Include`, output `./HarpiaTest/test_build` (all overridable via `HARPIA_INPUT_FILE`, `HARPIA_INCLUDE_FOLDER`, `HARPIA_OUTPUT_DIR`).

## Contents
- `test.harpia` — root input. Starts with `import "file3.harpia"` (resolved from `Include/`). Exercises messages, nested messages, enums, `optional`/`required`/`repeteable`, `map<>`, `pagination[N]`, and stream/pull/push/event message modifiers plus comment styles.
- `Include/file3.harpia` (`message queen` — the canonical example of the optional/required/map<K,V>-x3/pagination modifier combination, since `initiatives/feature-examples` Session EX.1 folded away the near-duplicate `pope`/`king`/`queenBee` that used to live in `file1.harpia`/`file2.harpia`/`file4.harpia`; plus fixtures added for specific generator features: `courier` — PUSH-only, exercises the ZMQ many-to-* runtime origin id; `parcel`/`shipment` — a repeated field targeting a table-less composed message (`RepeatedComposedField`); `waypoint`/`route`/`journey` — a composed field nested two levels deep inside an embedded table-less message) — the one module file pulled in by the root's `import` statement. **Only the root file's own md5 is used to tag every message** (see LexicalAnalizer/CLAUDE.md), so editing an Include file's content never perturbs the pinned `HASH` constants in `tests/` — this is why new fixtures land in Include files, not `test.harpia` itself.
- `test_build/` — GENERATED output (proto, generated/cpp adapters, CMake, server/client demo). Regenerated write-if-different each run, not wiped (`Util.util.write_if_different`/`prune_stale_outputs`, called from `main.py`) — an unchanged file keeps its mtime; a message renamed/removed since the last run has its old output pruned.
- `schema_registry/` — local sidecar (per-message `.fieldmap` files: `test/<MessageName>.fieldmap`), NOT generated output despite living next to `test_build/`. Written by `message/FieldMap.py` (see `message/CLAUDE.md`) to freeze each field's protobuf wire number across regenerations within a working tree. Deliberately outside `test_build/` so a wholesale rebuild of that dir can't blow it away. **git-ignored repo-wide** (`.gitignore`: `schema_registry/`) — project policy is not to commit it; it is regenerated on the first pipeline run in a fresh checkout (a no-op freeze from declaration order, identical output, as long as `test.harpia`'s fields haven't been reordered/removed since).

## Key facts / gotchas
- `test_build/` is **generated and gitignored** (repo `.gitignore` has `*build*`). Never edit by hand or commit; regenerate by running the pipeline.
- `schema_registry/` is also **git-ignored** (`.gitignore`: `schema_registry/`) and **never hand-edited** — a generation run writes it, but project policy is to regenerate it locally rather than commit it. It does NOT survive `git clean -x`; the next pipeline run re-freezes it. If you ever change a field's order or remove one in `test.harpia`, regenerate and eyeball the resulting `.fieldmap` the way you'd read a `.proto` field-number diff.
- Input md5 (current golden input, for detecting drift):

  - `Include/file3.harpia` = `c9babdce0a0f69e2de52991836fafeaf`
- Imports are resolved by filename against `includeFolder`; the root file references them bare (`file1.harpia`), not by relative path.
