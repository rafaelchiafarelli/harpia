# GradleAdapter — Java target: message-class generation (build-time Gradle wiring)

**Pipeline role:** Java-target Stage 6/7 equivalent (session J.2, `initiatives/multi-language-targets/thread-1-java-target`). Stands up a self-contained Gradle project under `<dest>/java/`, wired with `protobuf-gradle-plugin`, so the *consumer's* `gradle build` generates the Java message classes — harpia itself never shells out to `protoc` for Java. Per the codegen-timing decision (`initiatives/multi-language-targets/thread-1-java-target/histories/gRPC-wiring/codegen-timing-decision.md`), resolved build-time.
**Entry point (from main.py):** gated behind `HARPIA_GEN_LANG` (default `cpp`, unaffected): `if os.environ.get("HARPIA_GEN_LANG", "cpp") == "java": GradleAdapter(messages=msgFactory.messages, dest=testDestination, compliance=complianceContext).Process()`, called right after the `FileCreator` loop (needs `<dest>/proto/protofiles/*.proto` to already exist). Returns `None` or an `Error` (non-fatal; main.py logs it).
**Inputs → Outputs:** consumes message objects (`msg.name`, `msg.md5Hash` — same filename convention as `FileCreator`). Reads `<dest>/proto/protofiles/<name>_<hash>.proto` (already carrying `option java_multiple_files`/`java_package`, added in J.1). Emits `<dest>/java/build.gradle`, `<dest>/java/settings.gradle`, and a **copy** of each message `.proto` at `<dest>/java/src/main/proto/protofiles/<name>_<hash>.proto`.

## Files
- `GradleAdapter.py` — `Process()` makes `src/main/proto/protofiles/`, writes the two static Gradle files (`write_if_different`), then copies (`copy_if_different`) every message's `.proto` from `<dest>/proto/protofiles/` by reconstructing its filename from `(msg.name, msg.md5Hash)` — NOT a directory glob, so it can never accidentally pull in a `_service.proto` or the static framework protos (`errorCode.proto`/`heartBeat.proto`/`capabilities_service.proto`), which is deliberate: no gRPC yet (J.3), and those framework protos don't carry `java_package` yet either. Returns `NOTHING_TO_REPORT` (`Errors.Classes.MESSAGES`) if nothing was copied.
- `templates/project.gradle.tmpl` — written out as `<dest>/java/build.gradle`; named `project.gradle.tmpl`, not `build.gradle.tmpl`, purely because the repo's `.gitignore` has a broad `*build*` glob that would otherwise silently exclude the template file itself from version control. Static (no per-project substitution): `java` + `com.google.protobuf` (protobuf-gradle-plugin) plugins, `mavenCentral()`, `protobuf-java` + matching `protoc` artifact both pinned to `3.25.3`. No explicit `sourceSets` block — protobuf-gradle-plugin's default `src/main/proto` source dir is scanned recursively, which already covers the `protofiles/` subdirectory used here (and by every other `.proto`-emitting stage in this repo).
- `templates/settings.gradle.tmpl` — static: `rootProject.name = 'harpia_generated_java'`.

## Key facts / gotchas
- **Copies, does not reference, the source `.proto` tree.** `<dest>/java/` is deliberately self-contained (no `srcDir` reaching outside its own directory) — the thread's actual motivation (`../initiatives/multi-language-targets/thread-1-java-target/README.md` §7) is an Android app depending on a Gradle module built from this output, which needs to be portable on its own.
- **No `HARPIA_GEN_LANG`-style backend registry exists yet** (unlike `Database/backends`) — README §3 explicitly defers designing that seam until a second language exists. `main.py` does a plain `os.environ.get("HARPIA_GEN_LANG", "cpp")` string check; `GradleAdapter` itself has no language-selection logic of its own, it just always emits Java wiring when called.
- **Stale-output pruning needs no special-casing.** `Util.util.prune_stale_outputs` already walks the *entire* `<dest>` tree matching harpia's generic `<name>_<hash>...` pattern before any adapter runs, so a renamed/removed message's stale copy under `<dest>/java/src/main/proto/protofiles/` is cleaned up for free.
- protoc/`protoc-gen-grpc-java` are never invoked on the harpia generation host for Java — they're resolved by `protobuf-gradle-plugin` the first time `gradle build` runs against the emitted project, which needs network access to Maven Central (not available inside the harpia Docker image today; this is genuinely a "not part of the Docker image yet" gap, not an oversight — see `tests/test_java_gradle_wiring.py`'s gradle+JDK-gated integration test).
- Both template versions (`protobuf-gradle-plugin` 0.9.4, `protobuf-java`/`protoc` 3.25.3) are pinned known-good versions as of this session; bumping them is just editing the two template files, no code change.

## Touchpoints
- Called by: `main.py`, gated on `HARPIA_GEN_LANG=java`.
- Depends on: `Util.util.write_if_different`/`copy_if_different`/`loadTemplate`, `Logger.logger`, `Errors.Error`. Consumes `MessageCreator` messages and `ProtoFile.FileCreator`'s already-written `.proto` output (must run after the `FileCreator` loop).
- Consumed by: J.3 (gRPC stub wiring, adds the `protobuf-gradle-plugin` `grpc` plugin block + `protoc-gen-grpc-java` artifact + `_service.proto` wiring, and gives the framework protos their own `java_package`), J.22 (Gradle packaging, the fuller build.gradle this one only partially anticipates), J.25 (Android verification — consumes `<dest>/java/` as a Gradle module).
