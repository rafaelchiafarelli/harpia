# Message — semantic model: turns a message/enum token block into a typed object with fields

**Pipeline role:** Front-end, stage ~2–3 (semantic analysis). Consumed by `MessageCreator` (LexicalAnalizer) to build the intermediate representation the back-end `FileCreator` renders into proto/C++.
**Entry points:**
- `Message(fileName, availableMessages, md5Hash).Process(tokens)` → `None` or `Error`; called by `MessageCreator.CreateMessages`.
- Internally `Message.Process` constructs `Variables(...)` or `EnumValues(...)` and calls their `.Process()` then `.get()`.
**Inputs → Outputs:** a slice of tokens for one `message {...}`/`enum {...}` block → a `Message` with `.name`, `.variables` (list of `variable` or `(name,int)` enum tuples), `.access_modifiers`, `.tableName`, `.visibility`, `.isEnum`, `.dependency`.

## Files
- `Message.py` — `Message`: scans the block. Reads access modifiers (tokens between the preceding NEWLINE and the `message` keyword) e.g. `pull`/`event`/`stream` → sets `isOneToMany`. Name = ID token after `message`/`enum`. Between `{` and `}` delegates to `Variables` (message) or `EnumValues` (enum). For a non-enum message, immediately after `Variables.get()` it calls `FieldMap.freeze()` to overwrite the declaration-order indices with the frozen ones (or propagate its `Error`) — see `FieldMap.py` below. After `}`: a trailing `;` sets `visibility=PRIVATE`; a trailing ID sets `tableName`. `dependency` = composed-field type names.
- `Variables.py` — `variable` (POD: index, name, type tuple, regex, modifiers, typeMap, paginationSize, repeteableSize, constant, renamedFrom) and `Variables` (the field parser). Splits fields on `;`, detects modifiers `repeteable[N]`/`optional`/`unique`/`required`/`renamed_from[old]`/`pagination[N]`/`map<...>`, resolves type (scalar INT32/INT64/FLOAT/STRING, `map`, or a composed message name from `composedVariables`), and derives a validation regex. Assigns a **provisional** `index = len(variables)+1` (declaration order) — `Message.Process` immediately overwrites this via `FieldMap.freeze()`, so declaration order only matters for a field's number on the very first generation.
- `EnumValues.py` — `EnumValues`: two passes. First collects explicit `NAME = N;` values, sorts them, computes next free value; second pass assigns auto values to bare `NAME;` entries. Enforces unique values via `allUnique()`. Accepts 2-token (`NAME;`) or 4-token (`NAME = N;`) forms; each value must start its line. Not covered by `FieldMap` — enum member values are a separate numbering space from message field wire numbers, and are not (yet) frozen the same way.
- `FieldMap.py` — **stable wire-number field identity**, per `plans/message-versioning.md` §3. `freeze(variables, harpiaFile, messageName)` reads/writes a plain-text sidecar (`registry_path()`: `<dir of harpiaFile>/schema_registry/<harpiaFile stem>/<messageName>.fieldmap`, one `name:number` line per field plus an optional trailing `# reserved: 4,7` line) and reassigns each `variable.index` in place from it instead of from declaration order — the direct fix for the hazard in the bullet below. First generation for a message (no sidecar yet) just freezes the declaration order as-is. Later generations: a field keeps its old number if its name (or, for hidden fields, its *role* — see next bullet) is already in the sidecar; `renamed_from[old]` inherits `old`'s number if `old` is on record (a no-op fallback to plain new-field numbering otherwise, mirroring `Database/MigrationAdapter`'s own conditional RENAME); a name dropped from the sidecar is retired into `reserved`; a genuinely new field gets the lowest number never used live or retired. Returns `Error(RESERVED_FIELD_NUMBER_REUSED)` if a resolved number ever lands on a reserved one (only reachable via a hand-tampered sidecar today, since the DSL has no `field = N` syntax to trigger it directly) — a hard generation-time error, per the "never silently swallow a failure mode" convention `harpia_sensitive_data_design_rules.md` Rule 5 also uses.

## Key facts / gotchas
- **md5 hash drives hidden field names.** `Variables.__init__` auto-prepends `ID_<md5>` and `AddHiddenVariables` appends `STATUS_<md5>`, `ERROR_<md5>`, and `ORIGINATOR` (named `ORIGINATOR_<md5>` only when `isOneToMany`). Because `main.py` passes the ROOT file's md5 for every message, all messages across all imported files share the same hash suffix — a collision risk for the upcoming multi-root-file feature (two roots ⇒ different hashes; same root imported twice ⇒ identical suffixes). **This also means a hidden field's literal name changes on ANY edit to the `.harpia` file** (the md5 is over the whole file text) — `FieldMap` accounts for this by keying these four fields by role (`ID`/`STATUS`/`ERROR`/`ORIGINATOR`, matching `Database/model.py`'s own `_HIDDEN_PREFIXES` convention) rather than by literal name, so their wire numbers stay stable across hash changes the same way user fields' do.
- Composed (message-typed) fields: if `var.type[1] in composedVariables`, regex is set to the type itself and the type name is added to `self.dependencies` (1-to-many via link table when `repeteable`).
- **Mutable class-attribute bug in `EnumValues`:** `values = []` is a class attribute and `createValues` appends to it, so enum values can leak across `EnumValues` instances. `Variables`/`Message` mostly re-init lists in `__init__` (safer), but `Message`'s class-level defaults (`variables=None` etc.) are shadowed per-instance.
- `type` is stored as the raw token tuple `(TYPE, lexeme, line, col)`; downstream code reads `var.type[0]`/`[1]`.
- Regex constants live on `Variables` (RegexForInt/Float/String); `map` regex via `RegexForMaps`.
- **`schema_registry/` sidecars are committed source, not build output** — they live next to the `.harpia` file (e.g. `HarpiaTest/schema_registry/`), deliberately outside whatever `dest`/`HARPIA_OUTPUT_DIR` points at, because that build dir gets `rmtree`d/regenerated wholesale (see `tests/run_pipeline.py`) and losing the sidecar would defeat the whole point of freezing. Don't hand-edit; a message's field additions/removals/renames update it automatically on the next generation.

## Touchpoints

- Depends on: `Errors.Error`, `Logger.logger`, `uuid`, `Util.util.write_if_different` (via `FieldMap`). Consumed by back-end `FileCreator` (reads `variable.index` for the `.proto` field number).
