# ZmqCapabilityAdapter — ZMQ capability handshake (ZMQ slice)

**Pipeline role:** Stage 13 (zmq). Ships a hand-written client runtime and emits ONE whole-project REQ/REP responder advertising every message type the generated peer knows about. Part of the message-versioning capability-handshake effort (shipped 2026-08-23) — see `GrpcCapabilityAdapter/CLAUDE.md`/`Capability/CLAUDE.md` for the shared design and the sibling gRPC/HTTP slices.
**Entry points (from main.py):** `ZmqCapabilityAdapter(messages=msgFactory.messages, dest=testDestination, rootHash=rootFile.getHash()).Process()`. Returns `None`.
**Inputs → Outputs:** consumes the full `messages` list (via `Capability.capability_common.message_type_names`). Emits `<dest>/generated/cpp/capability/capabilities_<rootHash>_zmq.h` (`capabilities_responder`) and copies `harpia_zmq_capability.h` (client `negotiate()`) + the shared `harpia_capability_dispatch.h` into the same directory.

## Files
- `ZmqCapabilityAdapter.py` — same shape as `GrpcCapabilityAdapter.py`: copies both runtime headers, renders the template with the baked-in type list.
- `templates/capabilities_zmq.h.tmpl` — `harpia::zmq_capability::capabilities_responder`: a REP socket bound at construction; `serve_once()` blocks for one request (content ignored, any frame is treated as a query), replies with a `capabilities_Response` serialized the same way every other ZMQ sender in this project serializes a protobuf message (`SerializeToString` into a `zmq::message_t`). Caller drives the loop — same "caller owns the loop" convention as every other ZMQ receiver (`ZmqAdapter/templates/receiver.tmpl`), no internal `serve()` loop.
- `runtime/harpia_zmq_capability.h` — hand-written (NOT generated). `negotiate(ctx, endpoint, timeout, on_legacy_peer = noop)` opens a fresh REQ socket per call, sets `ZMQ_RCVTIMEO` to the requested timeout and `linger=0`, sends a `capabilities_Request`, and waits for a `capabilities_Response`. Any failure (send failure, recv timeout, unparseable reply) resolves uniformly to the plan's "legacy peer, no capability set" outcome.

## Key facts / gotchas
- **Reuses the exact same wire messages as gRPC and HTTP** (`capabilities_Request`/`capabilities_Response`, `Assets/proto/protofiles/capabilities_service.proto`) — just moved as raw serialized-protobuf ZMQ frames instead of a gRPC call or an HTTP body, the same way every other `ZmqAdapter`-generated sender/receiver already moves a message. No new wire format invented for ZMQ specifically.
- **REQ/REP was chosen over piggybacking on an existing PUSH/PULL or PUB/SUB pair** because the original design assumed ZMQ already has a "`stream[#]` setup phase" to hang the handshake on (from `initiatives/medical_devices/harpia_medical_master_plan.md` Track B) — **that phase does not exist in the actual codebase** (verified by grep: zero hits for "stream setup"/"StreamSetup"/`stream[#]` outside the aspirational, unstarted medical_devices plan). ZMQ has no existing metadata channel or session concept at all, so this is its own small self-contained request/reply exchange rather than piggybacking on something that isn't there.
- **Why the timeout signal is `recv()`, not `send()` or `connect()`**: ZMQ's async connect/send semantics mean both normally succeed even against a peer that's never shown up (they just queue) — this is deliberate ZMQ location-transparency, not a bug to work around. `ZMQ_RCVTIMEO` on the REQ socket is the one point that actually blocks on a real reply, so it's the only place a "legacy peer" (nothing ever bound at the endpoint) or a slow/unreachable peer can be distinguished from a healthy one.
- **`linger=0`** on the REQ socket — same `ZMQ_LINGER` gotcha already documented for CURVE in `ZmqAdapter/CLAUDE.md`: a socket destroyed with an unanswered/unsent message otherwise blocks on destruction indefinitely by default.
- **Whole-project artifact, not per-message** — same reasoning as `GrpcCapabilityAdapter`. Exactly one `capabilities_<rootHash>_zmq.h` regardless of schema size.
- **Only needs Stage 7 (`ProtoCompiler`)**, not Stage 13's `GrpcCompiler` — same as the HTTP slice, since neither rides gRPC.
- Fully verified for real in this environment (unlike the HTTP slice) — no `crow.h`/`asio` dependency at all, so it's unaffected by the pre-existing `third_party/asio` vendoring gap that currently blocks REST/SOAP/gRPC-unrelated tests. `tests/test_message_versioning_capability_zmq.py`'s two tests both pass end to end (real `inproc://` round trip; a real `tcp://` port with nothing listening for the legacy-peer path, chosen over `inproc://` there specifically because `inproc://` connect-before-bind semantics vary by libzmq version).
