# SerializeAdapter — unified JSON/XML/YAML `toString` façade + `phi` redaction

**Pipeline role:** Stage 10 (after `YamlAdapter`). Added by the serialization epic / Session serialization task 2 ("close out the JSON/XML/YAML `toString` triad through one shared path"); Session serialization task 3 wired `phi` redaction into that one hook; Session serialization task 4 added the audited opt-out from redaction. Ships three runtime headers + a generated registry + a thin per-message wrapper, plus a co-copy of Foundation F3's `harpia_audit_sink.h`.
**Entry points (from main.py):** `SerializeAdapter(messages=msgFactory.messages, dest=testDestination).Process()`. Returns `None` or `Error` (`NOTHING_TO_REPORT` when there are no messages).
**Inputs → Outputs:** consumes message objects (`msg.name`, `msg.md5Hash`, `msg.isEnum`, `msg.variables[].is_phi`). Emits `<dest>/generated/cpp/serialize/`: `<name>_<hash>_serialize.h` (wrappers), `harpia_phi_registry.h` (generated), and copies of `harpia_serialize.h` + `harpia_redaction.h` + `harpia_redaction_audit.h`; also co-copies `harpia_audit_sink.h` into `<dest>/generated/cpp/compliance/`. Enums skipped.

## Files
- `SerializeAdapter.py` — `Process()` copies the three static runtimes + co-copies `compliance/harpia_audit_sink.h` (via `Compliance.audit_common`), writes the generated `harpia_phi_registry.h`, then renders one wrapper per non-enum message. `_phi_pairs()` collects `(msg.name, v.name)` for every `v.is_phi` field (F2). Same overall structure as `YamlAdapter.py`.
- `templates/wrapper.h.tmpl` — thin per-message header: `#include`s `serialize/harpia_serialize.h` + the message's `.pb.h`. No per-message symbols.
- `runtime/harpia_serialize.h` — the façade (hand-written). `harpia::serialize::Format{JSON,XML,YAML}`, `to_string(const Message&, Format)`, `from_string(const std::string&, Message*, Format)`, `format_name(Format)`.
- `runtime/harpia_redaction.h` — the redaction control point (hand-written). `harpia::redaction::kPlaceholder` (`"[REDACTED]"`), `redaction_enabled()` (default **true**), `set_redaction_enabled(bool)` (low-level mechanism + F.3 test seam), `should_redact(message, field)` = `redaction_enabled() && phi::is_phi(...)`. `#include`s the generated registry. Compliance-free by design.
- `runtime/harpia_redaction_audit.h` — the **audited opt-out** (serialization task 4, hand-written). `harpia::redaction::allow_phi_print(AuditSink& = default_audit_sink(), reason = "")` emits one `record("phi_unredacted_output_enabled", "serialize.redaction", reason)` then `set_redaction_enabled(false)`; `restore_phi_redaction(AuditSink&)` flips it back then records `"phi_unredacted_output_disabled"`. The **only** place SerializeAdapter's runtime depends on the Compliance module — `#include`s `compliance/harpia_audit_sink.h` (co-copied by `Process()`); isolated here so `harpia_redaction.h` and the façade stay dependency-free. Not golden-snapshotted (static runtime, like the other two).
- `runtime/harpia_phi_registry.h` **is generated** by `SerializeAdapter.py`, not shipped from the repo — a `constexpr std::array<PhiField>` of the schema's `(message, field)` `phi` pairs + `is_phi()` / `message_has_phi()`. Golden-snapshotted under `UnitTests/golden/serialize/` (like `db/harpia_db_registry.h`); the two `harpia_*.h` static runtimes are **not** snapshotted (same convention as `harpia_xml.h`).

## Key facts / gotchas
- **serialization task 2: it is a dispatch layer, not a re-implementation.** For a message with **no `phi` field** (and no nested phi message), `to_string` is a straight pass-through: JSON → protobuf's own `MessageToJsonString` (default options — camelCase, proto3 defaults omitted, `ignore_unknown_fields=true` on parse — identical to `json/<name>_json.h`), XML → `::harpia::xml::to_xml`, YAML → `::harpia::yaml::to_yaml`. So JSON/XML output for non-`phi` messages is **byte-for-byte** what it was — the serialization task 2 acceptance gate — checked in golden by `test_golden.py` and at runtime by `test_non_phi_message_bypasses_redaction_path`.
- **serialization task 3: `phi` redaction happens here, once, for all three formats.** When `redaction_enabled()` (default) **and** the message tree (recursive, cycle-guarded `detail::tree_has_phi`) declares a `phi` field, `to_string` renders through `detail::redacted_to_string` — a self-contained, format-parameterised reflection walk that emits `[REDACTED]` (quoted for JSON/YAML, bare text for XML) for every `phi` field and formats every non-`phi` value by type. The three per-format engines (`harpia_xml.h`/`harpia_yaml.h`/protobuf JSON util) are **not touched** — no `#include` of a redaction header in them, no behaviour change. Cost: the redacting walk duplicates ~the XML/YAML emit logic inside `harpia_serialize.h` (~200 lines) — that is the deliberate price of "one hook, zero blast radius on the engines".
- **Redacted output is a lossy view, not a round-trip format.** `from_string` is unchanged (dispatches to the engines). Feeding a redacted JSON back (`"heart_rate":"[REDACTED]"` for a numeric field) fails the protobuf JSON parse → `from_string` returns `false`; redacted XML/YAML parse without error but leave the `phi` fields at their default. serialization task 5's round-trip test accounts for this.
- **The redacting walk's non-`phi` output is NOT guaranteed identical to the engines'** (e.g. it always prints proto3 default scalars, where protobuf-JSON omits them; float formatting is `std::to_string`). This only affects `phi`-bearing messages, whose output is allowed to change. Non-`phi` messages never enter this path.
- `harpia_serialize.h` `#include`s `xml/harpia_xml.h`, `yaml/harpia_yaml.h`, `serialize/harpia_redaction.h` (→ `serialize/harpia_phi_registry.h`) and `<google/protobuf/util/json_util.h>` — a TU including a `serialize/` wrapper needs `-I <cpp_root>` and (transitively via `harpia_xml.h`) `-I third_party/tinyxml2`.
- md5-hash-qualified wrapper filenames, same scheme as the sibling adapters.
